# 指示書：レシピ（セット撮影）機能とタブUI

作成：2026-11-16（同日改訂：既存プリセット実装との整合，未決事項の確定）．対象リポジトリ：esp32p4-cam（作業フォルダ /Users/katano/work/ESP32-P4/esp32p4-cam）．
優先度：高．2026-11-18（水）の部内定例報告で進捗を示す（§7の「定例までの到達目標」を参照）．

## 0．名称について（仮置き）

- 保存単位の呼び名は「レシピ」で仮置きする．UI表示名とドキュメント上の名称は後から一括で変えられるようにし，コード上の識別子は `recipe` / `step` を使う．
- 「プリセット」は，カメラパラメータ一式に名前を付けてボードに保存したもの．**実装済み**（コミット 210c989，`usb-app/API.md` §4.5）．今回は作り直さず，そのまま使う．

## 1．目的

XD4のテストピース撮影で，条件を少しずつ変えた複数枚を再現性よく撮るための機能を作る．

例：
- 同一の照明条件で，露出だけを5段階に変えた5枚を撮る
- 土台のプリセットは同じで，1枚目は右照明のみ，2枚目は左照明のみで撮る

あわせて，作業の見通しを上げるため，Web UI（`common/webui/index.html`）を機能ごとのタブ構成に改める．

## 2．前提（現行の仕組み．必ず先に読むこと）

- ボードAPIは `usb-app/API.md` が正本．カメラ設定は `GET/POST /ctrl`，能力範囲は `GET /ctrl/caps`，照明（MCP23017）は `GET/POST /io`（`light=0|1` の一括，`ch=0..7&on=0|1` の個別，`out=0..255` の一括指定がある），静止画は `GET /snapshot.jpg?q=`，照明付き撮影は `POST /shot`（ボード内リングは最新4枚まで）．
- 現在の設定はボードの `/cfg/config.json` に自動保存され（変更から約2秒後），再起動後も復元される．`/config/reset` で消える（プリセット自体は残る）．
- **プリセット（実装済み）**：`GET /presets`，`POST /presets/save|load|delete|rename?name=…`．保存先は `/cfg/presets.json`，最大20個，名前は UTF-8 で1〜48バイト（`"` `\` 制御文字は不可）．持つ項目は14項目：`exposure_mode`, `exposure_us`, `gain_mode`, `gain_index`, `focus_mode`, `focus_pos`, `wb_mode`, `wb_red`, `wb_blue`, `hflip`, `vflip`, `sp`, `shot_q`, `shot_light`．
  - `load` の副作用：ピントが `auto` のプリセットは読み込むたびにAFを1回走らせる．**向きが今と違うプリセットは保存してボードを再起動する**（約3秒503）．
  - 読み込み／保存したプリセット名は `/ctrl` の `preset` に，その後の変更有無は `preset_modified` に出る．`/ctrl` を変えると `preset_modified=true` になる．
  - 現行UIにはプリセット選択欄（上書き保存・名前を付けて保存・名前変更・削除）がある．
- UIは wifi-app（ボード配信）と usb-app（PCサーバー中継）で `common/webui/index.html` を共有する．**両方で同じように動くことが必須**．
- usb-appの中継（`usb-app/pc/server.py`）は，メソッド・パス・クエリに加えて**リクエストボディもボードへ転送する**（`httpch.py` がボディに Content-Length を付けて送る）．ただし中継を通るメソッドは **GET と POST のみ**（PUT／DELETE は通らない）で，ボードへの同時リクエストは3本まで（`API_SLOTS`）．**新APIの操作はすべて GET／POST で表すこと（削除も POST）**．応答ヘッダーは中継が通すものが限られる（`PASS_HEADERS` の6種のみ）．
- ボード側ハンドラは現在すべてクエリのみで動いており，ボディを読む処理（`httpd_req_recv`）はどこにも無い．`httpd_req_recv` 自体は ESP-IDF 標準でリンク済みなので，新規ハンドラに足せば使える見込み（§2.5で確認）．
- ボードの保存領域は LittleFS 1MB（`storage` パーティション）．既存の JSON 読み込みは `CFG_READ_MAX`（24kB）で頭打ちにしている．
- 照明の物理的な対応（どのOUTが右照明／左照明か）はボード側の配線と `pins.h` の `LIGHT_MASK` が決める．UIとレシピではOUT0〜OUT7のチャンネル番号で扱い，右／左などの名前は付けない．
- 現行のギャラリー（`shots`）は**12枚で古いものから破棄**される（`index.html` の `shots.length>12`）．

## 2.5．着手時の確認タスク（フェーズ0．最初に実施．短時間で済ませる）

レシピの保存は **POST＋JSONボディ** を第一案とする（ステップ配列をそのまま送れ，途中失敗の扱いが単純なため）．次を確認して確定する．

1. camcore に `POST /recipes/save` の仮ハンドラを足し，`httpd_req_recv` で `req->content_len` 分を受け取ってログに出す．
2. wifi-app（ボード直接）と usb-app（中継経由）の両方から，数kB の JSON を curl で送って受け取れることを確かめる．
3. 受け取れれば第一案で進める．受け取れない，または中継側の修正が大掛かりになる場合のみ，クエリ方式（作成→1ステップずつ追加→確定 の分割POST）に切り替える．
4. どちらにしたかと根拠を，`usb-app/API.md` と `HANDOFF.md` に記録する．

## 3．要件1：プリセット（既存を使う．追加は最小限）

- 新規のプリセットAPIは作らない．既存の `/presets` 一式を使う．
- プリセットが持つ項目は既存どおり14項目（向き・`sp`・`shot_q`・`shot_light` を含む）とする．
- 「値を指定して保存」は今回は作らない（今の状態から保存で足りる．必要になれば別途）．
- 追加するのは UI 側のみ：プリセットタブへの移設（§6）と，JSONエクスポート（§5.5）．

## 4．要件2：レシピ（データモデルと保存API）

レシピは次の構造とし，ボードの `/cfg/recipes.json` に保存する．

```json
{
  "name": "露出ブラケット5段",
  "base_preset": "標準",
  "steps": [
    {"enabled": true,  "overrides": {"exposure_mode": "manual", "exposure_us": 4000}, "light_out": 3, "q": 95, "settle_ms": 800},
    {"enabled": true,  "overrides": {"exposure_us": 8000}, "light_out": 3, "q": 95, "settle_ms": 800}
  ]
}
```

- `name`：プリセットと同じ制約（UTF-8で1〜48バイト，`"` `\` 制御文字は不可）．
- `base_preset`：土台にするプリセット名．`null` の場合は実行開始時点のボードの現在設定を土台とする．
- `steps[].overrides`：そのステップで変える項目だけを書く．書かれていない項目は土台の値を継承する．上書きできるのは次の9項目：`exposure_mode`, `exposure_us`, `gain_mode`, `gain_index`, `focus_mode`, `focus_pos`, `wb_mode`, `wb_red`, `wb_blue`．**向き（`hflip`/`vflip`）・`sp`・`shot_q`・`shot_light` は上書きできない**（向きは再起動を伴うため）．
- `steps[].light_out`：照明の出力マスク（0〜255，ビット0=OUT0）．`null` の場合は照明を操作しない（その時点の状態のまま）．
- `steps[].q`：JPEG品質（1〜100）．省略時は95．
- `steps[].settle_ms`：条件を適用してから撮影するまでの待ち時間（ms）．省略時は800．
- `steps[].enabled`：`false` のステップは実行時に飛ばす．
- 上限：レシピ20件，1レシピ30ステップ．`recipes.json` は既存の `CFG_READ_MAX`（24kB）を超えうるので，レシピ用に上限を別に設けるか，レシピごとにファイルを分ける（どちらにしたかを API.md に書く）．読み込みバッファはスタックではなくヒープに取る．
- ボードはレシピの中身を検証する（キー名・値の範囲・型．不正なら 400 `{"error": ...}`）．`base_preset` が存在するかは保存時には問わない（実行時にUIが確認する）．

API（既存の流儀に合わせる．JSON応答，エラーは `{"error": ...}`，操作はすべて GET／POST）：

- `GET /recipes`：全件．`{"max": 20, "max_steps": 30, "recipes": [ ... ]}`．
- `POST /recipes/save`：ボディにレシピ1件のJSON．同名があれば上書き（順番はそのまま）．応答は `GET /recipes` と同じ形．
- `POST /recipes/delete?name=…`：削除．
- `POST /recipes/rename?name=…&to=…`：名前変更（任意．時間が無ければ後回し可）．

`camctl.h` の `CAMCTL_URI_COUNT`（またはレシピ用モジュールの URI 数）と，camcore.c の `max_uri_handlers` の計算を忘れず更新する．

## 5．要件3：レシピの実行

- 実行はブラウザ側（webuiのJavaScript）が担う．ボードに実行エンジンは作らない．
- **開始前の確認**：
  - `base_preset` が指定されていて存在しなければ，実行しない（エラー表示）．
  - そのプリセットの `hflip`/`vflip` が今の向きと違う場合は，実行しない．「先にプリセットタブでそのプリセットを読み込んでください（ボードが再起動します）」と表示する．レシピ実行中に再起動を起こさないため．
- **開始時**：実行前の `/ctrl` の値，`/io` の `out`，選択中プリセット名と `preset_modified` を記録する．`base_preset` があれば `POST /presets/load?name=…` で読み込む（ピント `auto` ならAFが1回走る．これは許容する）．
- **1ステップの流れ**：`light_out` が指定されていれば `POST /io?out=<mask>` → `overrides` を `POST /ctrl` で適用 → `settle_ms` 待つ → `GET /snapshot.jpg?q=<q>` で撮影し，結果をギャラリーへ追加する．
  - 前のステップの上書きは次のステップに持ち越さない．各ステップの前に，土台の値（`base_preset` の値，または開始時に記録した値）のうち，前ステップで上書きした項目を戻してから，そのステップの `overrides` を当てる．
  - `/shot` のリング（4枚）を使う方式は，5枚以上のレシピで溢れるため使わない．照明は `/io` で点けたまま `snapshot.jpg` を撮る（現行仕様で可能）．
  - 撮影のたびにプレビューを止めて帯域を譲る，既存のシャッター処理の流儀に合わせる．
- **終了時（正常終了・中断・失敗とも）**：照明を開始前の `out` に戻す．カメラ設定は，開始前に未変更のプリセットを選んでいた場合は `POST /presets/load` でそれを読み直し，そうでなければ記録した `/ctrl` の値を `POST /ctrl` で戻す．
- 実行中は進捗を表示する（何ステップ目／全何ステップか，実行中ステップの内容）．**中断ボタン**を用意し，押されたら現在のステップが終わった時点で止める．実行中はシャッター（Spaceキー含む）とプリセット操作を無効にする．
- 結果のファイル名は `<レシピ名>_NN_<時刻>.jpg`（NNは01始まりのステップ番号，時刻は `YYYYMMDD-HHMMSS`）．レシピ名のうちファイル名に使えない文字（`\ / : * ? " < > |` と空白）は `_` に置き換える．
- 失敗したステップ（APIエラー等）があっても全体を止めず，そのステップを失敗として記録して次へ進む．終了時に成功／失敗の数を表示する．
- **ギャラリーの上限**：レシピの結果は通常の12枚上限とは別に，直近1回の実行分を全数保持する（次の実行を始めたら前回分を破棄する）．「全部保存」ボタンで1枚ずつ順にダウンロードできるようにする（ZIP化は不要）．

## 5.5．要件：JSONエクスポートと撮影条件の保持（他メンバー共有・データセット連携）

- プリセットとレシピは，Web UI から JSON ファイルとしてエクスポートできること．プリセット全件（`GET /presets` の `presets` 配列）と，レシピ全件（または選択した1件）を，ボードの保存内容と一致する JSON でダウンロードできるボタンを，プリセットタブとレシピタブに置く．他メンバーへの仕様共有と，依頼があったときの提出に使う．
- インポート（JSONからボードへ書き戻す）は今回は作らない．
- エクスポート形式は §2（プリセット14項目）・§4 のデータモデルそのものとする．各キーの意味と単位，継承ルールは `usb-app/API.md` に書き，他メンバーが JSON と API.md だけで構造を理解できるようにする．
- レシピ実行の結果は，写真ごとに実際に適用された実効条件を保持すること．継承を解決した最終値（上書き可能な9項目）に，`light_out`（実際の出力値．`null` 指定のステップは撮影時点の `/io` の値），`q`，ステップ番号，撮影時刻を加え，ギャラリーの各写真に紐付けて表示できること．実効値は送った値ではなく，撮影直前に `GET /ctrl` で読み戻した値を使う（ボードが範囲に丸めるため）．
- 実行結果はマニフェスト JSON としてエクスポートできること．データセット側が，写真と撮影条件をセットで取り込める形にする．写真との対応はファイル名で取る．形式の例：

```json
{
  "recipe": "露出ブラケット5段",
  "base_preset": "標準",
  "executed_at": "2026-11-16T09:00:00+09:00",
  "shots": [
    {"file": "露出ブラケット5段_01_20261116-090000.jpg", "step": 1, "ok": true,
     "taken_at": "2026-11-16T09:00:00+09:00",
     "applied": {"exposure_mode": "manual", "exposure_us": 4000},
     "light_out": 3, "q": 95}
  ]
}
```

（`applied` には9項目すべての最終値を入れる．上の例は省略表記．失敗したステップは `"ok": false` と `"error"` を入れ，`file` は `null`．）

## 6．要件4：タブUI

`common/webui/index.html` を，機能ごとのタブで管理する構成に改める．

- プレビューとシャッターボタンはタブの外に常時表示する（撮影しながら条件を変えるため）．
- タブの構成：「カメラ」（露出・ピント・WB・向き・撮影設定），「照明」（現行の照明ON/OFF＋OUT0〜7の個別操作），「プリセット」（既存のプリセット欄を移設．一覧・保存・適用・名前変更・削除・JSONエクスポート），「レシピ」（一覧・ステップ表エディタ・実行・JSONエクスポート），「写真」（ギャラリー，撮影条件の表示とマニフェストJSON出力）．
- 選択中のタブは localStorage に覚えてよい（表示上の便宜であり，制御の状態ではないため）．
- レシピの編集は**ステップ表**で行う．1行＝1ステップ，列は 有効／シャッター（µs）／ゲイン／ピント／WB赤／WB青／照明（OUT0〜7のチェック＋「操作しない」）／画質／待機ms．
  - 「空欄は土台を継承する」を表の見出しに明記する．
  - モードの列は設けない．シャッターに値を入れたら `exposure_mode=manual` も上書きする（ゲイン→`gain_mode`，ピント→`focus_mode`，WB赤・青のどちらか→`wb_mode` も同様に `manual`）．値の範囲は `GET /ctrl/caps` に合わせる．
  - 行の追加・複製・削除・上下移動ができること．土台プリセットの選択（「なし＝現在設定」を含む）とレシピ名の入力，保存ボタンを置く．
- 既存機能の回帰がないこと：プレビュー（サイズ・画質），シャッター（Spaceキー含む），照明ON/OFF，露出・ピント・WBの各操作，AF，ワンプッシュWB，向き変更（再起動待ち処理），撮影設定（画質・照明），プリセット操作，設定リセット，物理ボタンの写真の自動取り込み．

- 作業ツリーに残っている tunnel／rev1 関連の未コミット変更（`tunnel.c`，`tunnel.py`，`sdkconfig.rev1` など）は本件と無関係．混ぜてコミットしない．
- フェーズ分け：
  - フェーズ0＝§2.5 のボディ受け取り確認と方式決定．
  - フェーズ1＝レシピの保存API（ボード側）．
  - フェーズ2＝タブUI（既存機能の移設のみ）．
  - フェーズ3＝ステップ表エディタと実行．
  - フェーズ4＝エクスポート（プリセット・レシピ・マニフェスト）．
  - 各フェーズで usb-app と wifi-app の両方のビルドが通る状態にし，進捗をコミットに残す．
- **定例（11/18）までの到達目標**：フェーズ0〜2 と，フェーズ3のうち「露出5段レシピをUIから作って実行できる」まで．エクスポートと細部は定例後でよい．
- `usb-app/API.md` と `HANDOFF.md` を実装に合わせて更新する．
- KLAYERSボード（ESP32-C6なし）でも動くこと．camcore側にWi-Fi前提のコードを入れない．

## 8．受け入れ条件

1. 既存プリセットに回帰がない（保存・再起動後も一覧に残る・適用で `/ctrl` が保存時と一致）．
2. 露出5段のレシピ（同一照明，`exposure_us` のみ変更）を保存し，ボードを再起動しても残る．実行すると5枚撮れ，各写真の明るさが段階的に変わる．画面表示で各ステップに適用した値が確認できる．
3. 照明ステップのレシピ（1枚目 `light_out`=右照明のOUTのみ，2枚目=左照明のOUTのみ）を実行すると，照明の付き方が写真ごとに切り替わる．
4. 実行後（中断を含む），照明とカメラ設定が実行前の状態に戻る．
5. 向きが今と違う土台プリセットのレシピは，実行前に止まり理由が表示される（再起動しない）．
6. usb-app（PCサーバー中継経由）と wifi-app（ボード直接）の両方で，レシピの保存・実行ができる．
7. タブUIで既存機能に回帰がない（§6の列挙項目を一通り操作できる）．
8. 実行の中断が効く．失敗ステップがあっても残りのステップが実行される．13枚以上のレシピでも全写真が残る．
9. プリセットとレシピを UI から JSON エクスポートでき，内容がボードの保存内容と一致する．
10. レシピ実行後，写真ごとの実効条件を含むマニフェスト JSON を出力でき，ファイル名で写真と対応が取れる．
