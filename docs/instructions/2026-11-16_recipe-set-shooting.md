## 0．名称について（仮置き）

- 保存単位の呼び名は「レシピ」で仮置きする．UI表示名とドキュメント上の名称は後から一括で変えられるようにし，コード上の識別子は `recipe` / `step` を使う．
- 「プリセット」は，カメラパラメータ一式に名前を付けてボードに保存したもの．**実装済み**（コミット 210c989，`usb-app/API.md` §4.5）．今回は作り直さず，そのまま使う．
- 「レシピ」と「ラン計画」は別物．レシピは使い回す撮り方の定義（ボードに保存）．ラン計画は，ある試験片をあるレシピで1回撮るときの予定表と進捗（実行開始時に UI が作り，ボードは直近1件だけ持つ）．

## 1．目的

XD4のテストピース撮影で，条件を少しずつ変えた複数枚を再現性よく撮るための機能を作る．

例：
- 同一の照明条件で，露出だけを5段階に変えた5枚を撮る
- 土台のプリセットは同じで，1枚目は右照明のみ，2枚目は左照明のみで撮る

あわせて，作業の見通しを上げるため，Web UI（`common/webui/index.html`）を機能ごとのタブ構成に改める．

## 2．前提（現行の仕組み．必ず先に読むこと）

- ボードAPIは `usb-app/API.md` が正本．カメラ設定は `GET/POST /ctrl`，能力範囲は `GET /ctrl/caps`，照明（MCP23017）は `GET/POST /io`（`light=0|1` の一括，`ch=0..7&on=0|1` の個別，`out=0..255` の一括指定がある），静止画は `GET /snapshot.jpg?q=`，照明付き撮影は `POST /shot`（ボード内リングは最新4枚まで）．
- **値の書き方はボードの `/ctrl` に従う**（2026-11-17 ユーザー決定）：モードは `"auto"`／`"manual"`，`wb_red`・`wb_blue` は整数（1000 = ×1.0），`sp` は `"A"`／`"B"`，`shot_light` は `true`／`false`．転送フォーマット仕様もこれに合わせる．
- 現在の設定はボードの `/cfg/config.json` に自動保存され（変更から約2秒後），再起動後も復元される．`/config/reset` で消える（プリセット自体は残る）．
- **プリセット（実装済み）**：`GET /presets`，`POST /presets/save|load|delete|rename?name=…`．保存先は `/cfg/presets.json`，最大20個，名前は UTF-8 で1〜48バイト（`"` `\` 制御文字は不可）．持つ項目は12項目：`exposure_mode`, `exposure_us`, `gain_mode`, `gain_index`, `focus_mode`, `focus_pos`, `wb_mode`, `wb_red`, `wb_blue`, `sp`, `shot_q`, `shot_light`．**向き（`hflip`／`vflip`）は含めない**（2026-11-16 ユーザー決定．210c989 は向きを含む14項目だったので外した（2c72679）．既存の presets.json に向きキーがあっても，読み込み時に無視する）．
  - `load` の副作用：ピントが `auto` のプリセットは読み込むたびにAFを1回走らせる．向きは含めないので，`load` でボードが再起動することはない（210c989 の再起動動作は除去済み）．
  - **実装上の注意（落とし穴．対応済み）**：`camctl.c` の `settings_to_json_locked()` は，プリセットの書き出し（`presets.json`）と `config.json` の保存（`save_now()`）の両方で使われている．この関数から `hflip`/`vflip` を消すと `config.json` にも向きが残らず，再起動で向きが戻ってしまう．**`config.json` には向きを残し，プリセットからだけ外す**（関数に「向きを含めるか」の引数を足した）．
  - 向きを変えても `preset_modified` は `true` にしない（向きはプリセットの項目ではないため．対応済み）．
  - 読み込み／保存したプリセット名は `/ctrl` の `preset` に，その後の変更有無は `preset_modified` に出る．向き以外の `/ctrl` を変えると `preset_modified=true` になる．
- UIは wifi-app（ボード配信）と usb-app（PCサーバー中継）で `common/webui/index.html` を共有する．**両方で同じように動くことが必須**．
- usb-appの中継（`usb-app/pc/server.py`）は，メソッド・パス・クエリに加えて**リクエストボディもボードへ転送する**（`httpch.py` がボディに Content-Length を付けて送る）．ただし中継を通るメソッドは **GET と POST のみ**（PUT／DELETE は通らない）で，ボードへの同時リクエストは3本まで（`API_SLOTS`）．**新APIの操作はすべて GET／POST で表すこと（削除も POST）**．応答ヘッダーは中継が通すものが限られる（`PASS_HEADERS` の6種のみ）．usb-app の回線は約 200 KB/s と細いので，繰り返し送るものは小さくする．
- ボディを読む処理は `recipe.c`（`POST /recipes/save`）にある．同じ書き方で新しいハンドラにも足せる．
- ボードの保存領域は LittleFS 1MB（`storage` パーティション）．既存の JSON 読み込みは `CFG_READ_MAX`（24kB）で頭打ちにしている（レシピは別の上限 240kB）．
- 照明の物理的な対応（どのOUTが右照明／左照明か）はボード側の配線と `pins.h` の `LIGHT_MASK` が決める．UIとレシピではOUT0〜OUT7のチャンネル番号で扱い，右／左などの名前は付けない．
- ギャラリー（`shots`）は通常の撮影分を**12枚で古いものから破棄**する．レシピの結果は別枠（§5）．

## 2.5．着手時の確認タスク（フェーズ0．済み）

レシピの保存は **POST＋JSONボディ** を第一案とした（ステップ配列をそのまま送れ，途中失敗の扱いが単純なため）．

1. camcore に `POST /recipes/save` のハンドラを足し，`httpd_req_recv` で `req->content_len` 分を受け取る．
2. wifi-app（ボード直接）と usb-app（中継経由）の両方から，数kB の JSON を curl で送って受け取れることを確かめる．
3. 受け取れれば第一案で進める．受け取れない，または中継側の修正が大掛かりになる場合のみ，クエリ方式（作成→1ステップずつ追加→確定 の分割POST）に切り替える．
4. どちらにしたかと根拠を，`usb-app/API.md` と `HANDOFF.md` に記録する．
5. `POST /run`（ラン計画の登録，§5）も JSON ボディが前提である．ボディが使えないと判明した場合は，ラン計画の登録方法を別途考える必要があるため，フェーズ0の結果報告にその旨を必ず含めること．

**結果**：usb-app 経由で受け取れたので第一案（ボディ方式）に決定．30ステップ（7.9 kB）も保存でき，空のボディは 400，12 kB 超は 413．途中で見つかった UART 受信あふれは修正済み（bc8dae5）．ボディが使えるので，`POST /run` もボディ方式で問題ない．wifi-app（ボード直接）での確認は未実施．

## 4．要件2：レシピ（データモデルと保存API）

レシピは次の構造とし，ボードの `/cfg/recipes.json` に保存する．

```json
{
  "name": "露出ブラケット5段",
  "base_preset": "標準",
  "steps": [
    {"enabled": true,  "overrides": {"exposure_mode": "manual", "gain_mode": "manual", "exposure_us": 4000}, "light_out": 3, "q": 95, "settle_ms": 800},
    {"enabled": true,  "overrides": {"exposure_mode": "manual", "gain_mode": "manual", "exposure_us": 8000}, "light_out": 3, "q": 95, "settle_ms": 800}
  ]
}
```

- `name`：プリセットと同じ制約（UTF-8で1〜48バイト，`"` `\` 制御文字は不可）．
- `base_preset`：土台にするプリセット名．`null` の場合は実行開始時点のボードの現在設定を土台とする．
- 【v1】`base_values`：土台の値の控え（12項目）．**ボードは受け付けて保存する（任意項目．12項目のキーと値を検証する）が，UI のエディタはボードに保存するときには付けない**（プリセットを直したらレシピにも反映される，という今の動きを保つため）．書き出し（§5.5）のときに UI が埋める．実行時に `base_values` があれば，それを土台にする（§5）．
- `steps[].overrides`：そのステップで変える項目だけを書く．書かれていない項目は土台の値を継承する．上書きできるのは次の9項目：`exposure_mode`, `exposure_us`, `gain_mode`, `gain_index`, `focus_mode`, `focus_pos`, `wb_mode`, `wb_red`, `wb_blue`．**向き（`hflip`/`vflip`）・`sp`・`shot_q`・`shot_light` は上書きできない**（向きは再起動を伴うため．画質はステップの `q` で指定する）．
- `steps[].light_out`：照明の出力マスク（0〜255，ビット0=OUT0）．`null` の場合は照明を操作しない（その時点の状態のまま）．
- `steps[].q`：JPEG品質（1〜100）．省略時は95．
- `steps[].settle_ms`：条件を適用してから撮影するまでの待ち時間（ms）．省略時は800．
- `steps[].enabled`：`false` のステップは実行時に飛ばす．
- 上限：レシピ20件，1レシピ30ステップ，1件のボディ 12 kB，`recipes.json` の読み込み 240 kB（API.md に記載済み）．読み込みバッファはヒープ（PSRAM）に取る．
- ボードはレシピの中身を検証する（キー名・値の範囲・型．不正なら 400 `{"error": ...}`）．`base_preset` が存在するかは保存時には問わない（実行時にUIが確認する）．

API（既存の流儀に合わせる．JSON応答，エラーは `{"error": ...}`，操作はすべて GET／POST）：

- `GET /recipes`：全件．`{"max": 20, "max_steps": 30, "recipes": [ ... ]}`．（済み）
- 【v1】`GET /recipes?name=<名前>`：指定した1件のレシピオブジェクトを返す．無い名前には 404 `{"error": ...}`．
- `POST /recipes/save`：ボディにレシピ1件のJSON．同名があれば上書き（順番はそのまま）．応答は `GET /recipes` と同じ形．（済み）
- `POST /recipes/delete?name=…`：削除．（済み）
- `POST /recipes/rename?name=…&to=…`：名前変更．（済み）
- 【v1】ラン計画（§5）．ボードは直近1件だけを RAM に持つ（再起動で消える）．
  - `POST /run`：ボディにラン計画 JSON（転送フォーマット仕様 §6）．実行開始時に1回だけ送る．前のラン計画と置き換わる．ボディの上限 16 kB．ボードは `format`・`version`・`run_id`・`expected_count`・`steps` の形を確かめ，`status` を `running`，`done_count` を 0 にして保持する．応答は `GET /run` と同じ形．
  - `POST /run/update?run_id=…&done_count=…&status=…`：進捗の更新．`done_count` と `status` はどちらか一方でもよい．`run_id` が保持中のラン計画と違う，またはラン計画が無いときは 409（古いタブからの更新で上書きしないため）．`status` は `running`／`done`／`stopped`／`error`，`done_count` は 0〜`expected_count`，範囲外は 400．
  - `GET /run`：`{"run": <ラン計画 または null>, "age_ms": <最後に登録・更新されてからのミリ秒 または null>}`．ラン計画が無いときは `{"run": null, "age_ms": null}`（200）．ボードには時計が無いので経過時間で返す．`status` が `running` のまま `age_ms` が大きければ，実行役のブラウザが止まったと判断できる．

`recipe.h` の `RECIPE_URI_COUNT`（ラン計画を別モジュールにするならその URI 数）と，camcore.c の `max_uri_handlers` の計算を忘れず更新する．ラン計画は3つ増える（`GET /run`，`POST /run`，`POST /run/update`）．

## 5．要件3：レシピの実行

- 実行はブラウザ側（webuiのJavaScript）が担う．ボードに実行エンジンは作らない．
- **開始前の確認**：
  - `base_values` が無く，`base_preset` が指定されていて存在しなければ，実行しない（エラー表示）．
- **土台の解決順**【v1】：`base_values` があればそれ → 無ければ `base_preset` のプリセット → `base_preset` が `null` なら実行開始時点の現在設定．
- **開始時**：実行前の `/ctrl` の値，`/io` の `out`，選択中プリセット名と `preset_modified` を記録する．土台が `base_preset` なら `POST /presets/load?name=…` で読み込む（ピント `auto` ならAFが1回走る．これは許容する）．【v1】土台が `base_values` なら，その12項目を `POST /ctrl` で当てる．
- 【v1】**ラン計画の登録（データセット側への事前申告）**：実行開始時に，操作者がレシピタブの実行画面で試験片ID（`specimen_id`）を入力する．UI は `run_id`（開始時刻ベースで一意．`YYYYMMDD-HHMMSS`）を振り，ラン計画（転送フォーマット仕様 §6 の形式．有効なステップごとに，継承を解決した実効条件9項目＋`sp` と，`light_out`，`q` を含む．`expected_count` は有効ステップ数）を `POST /run` でボードに登録する．登録に失敗しても撮影は続け，失敗したことを画面に出す．
- **1ステップの流れ**：`light_out` が指定されていれば `POST /io?out=<mask>` → `overrides` を `POST /ctrl` で適用 → ピントが `auto` ならAFの完了を待つ → `settle_ms` 待つ → `GET /ctrl` で実効値を読み戻す → `GET /snapshot.jpg?q=<q>` で撮影し，結果をギャラリーへ追加する．
  - 前のステップの上書きは次のステップに持ち越さない．各ステップの前に，土台の値のうち，前ステップで上書きした項目を戻してから，そのステップの `overrides` を当てる．
  - `/shot` のリング（4枚）を使う方式は，5枚以上のレシピで溢れるため使わない．照明は `/io` で点けたまま `snapshot.jpg` を撮る．
  - 撮影のたびにプレビューを止めて帯域を譲る，既存のシャッター処理の流儀に合わせる．
- 【v1】**ラン計画の更新**：ステップが終わるたびに（成功・失敗とも）`POST /run/update?run_id=…&done_count=<終わった数>`，終了時に `POST /run/update?run_id=…&status=done|stopped|error` を送る（`stopped`＝中断，`error`＝開始時の失敗など全体が続けられなかったとき．失敗ステップがあっても最後まで回れば `done`）．更新の失敗では撮影を止めない．データセット側は `GET /run` をポーリングして，進行と到着予定を把握する．
- **終了時（正常終了・中断・失敗とも）**：照明を開始前の `out` に戻す．カメラ設定は，開始前に未変更のプリセットを選んでいた場合は `POST /presets/load` でそれを読み直し，そうでなければ記録した `/ctrl` の値を `POST /ctrl` で戻す．
- 実行中は進捗を表示する（何ステップ目／全何ステップか，実行中ステップの内容）．**中断ボタン**を用意し，押されたら現在のステップが終わった時点で止める．実行中はシャッター（Spaceキー含む）とプリセット操作を無効にする．
- 結果のファイル名は `<レシピ名>_NN_<時刻>.jpg`（NNは01始まりのステップ番号，時刻は `YYYYMMDD-HHMMSS`）．レシピ名のうちファイル名に使えない文字（`\ / : * ? " < > |` と空白）は `_` に置き換える．
- 失敗したステップ（APIエラー等）があっても全体を止めず，そのステップを失敗として記録して次へ進む．終了時に成功／失敗の数を表示する．
- **ギャラリーの上限**：レシピの結果は通常の12枚上限とは別に，直近1回の実行分を全数保持する（次の実行を始めたら前回分を破棄する）．「全部保存」ボタンで1枚ずつ順にダウンロードできるようにする（ZIP化は不要）．【v1】写真と一緒に，同名のマニフェスト（§5.5）も保存する．

## 5.5．要件：JSON書き出しと撮影条件の保持（他メンバー共有・データセット連携）

書き出しとマニフェストの形式は，**「レシピ転送フォーマット仕様 v1」（`docs/instructions/recipe-transfer-format.md`，2026-11-17 制定）** に一致させる．要点をここにも書く．現行の書き出し（`presets.json`，レシピ単位の JSON，実行1回分のマニフェスト）は，この形式に置き換える．

- 【v1】バンドル書き出し：プリセットとレシピの受け渡しは，1つの JSON バンドル（`{"format": "esp32p4-cam/recipe-bundle", "version": 1, "exported_at": ISO8601, "presets": [...], "recipes": [...]}`，ファイル名は `recipe-bundle_YYYYMMDD-HHMMSS.json`，インデント2スペース）で行う．**バンドル専用のエンドポイントは作らない**．Web UI が `GET /presets`・`GET /recipes`・`GET /ctrl` の応答から組み立て，ダウンロードさせる．ボタンはプリセットタブとレシピタブに置く．
- 【v1】プリセットのバンドル表記は `{"name", "values"}` で，`values` は12項目（向きを含めない）．ボードの `GET /presets` 応答は設定を名前と同じ階層に持つ形なので，UI が `values` に包み直す．部分項目だけのプリセットもそのまま出す（無い項目は適用時に変更しない，という意味を保つ）．
- 【v1】レシピのバンドル表記（**受け手が継承を解決しなくて済む形**．2026-11-17 ユーザー決定）：
  - `base_values`：土台の12項目すべて．`base_preset` があればそのプリセットの書き出し時点の内容（部分項目なら書き出し時点の現在値で補完）．`base_preset` が `null` なら書き出し時点の現在値．
  - 各ステップに `values`（`base_values` に `overrides` を重ねた，解決済みの12項目）を書く．`overrides` も残す（何を振っているレシピかが分かるように）．
  - 受け手は各ステップの `values`・`light_out`・`q`・`settle_ms` だけ読めば撮影条件が分かる．
- インポート（JSONからボードへ書き戻す）は今回は作らない．
- 【v1】マニフェスト：レシピ実行で得た写真には，写真と同名で拡張子だけ `.json` にしたマニフェストを付ける（仕様書 §5 の形式．`{"format": "esp32p4-cam/shot-manifest", "version": 1, "photo", "run_id", "specimen_id", "recipe", "step_index", "taken_at", "effective", "light_out", "q"}`）．
  - `effective` は継承を解決した最終値（9項目＋`sp`）で，送った値ではなく撮影直前に `GET /ctrl` で読み戻した値を使う（ボードが範囲に丸めるため）．
  - `light_out` は実際の出力値とする（`null` 指定のステップは撮影時点の `/io` の値）．
  - レシピ実行で得た写真では，ラン計画の `run_id` と `specimen_id` を入れ，写真とラン計画を対応付ける．
  - 通常のシャッター（レシピ外）で撮った写真では，`run_id`・`specimen_id`・`recipe`・`step_index` を `null` とし，撮影時の現在値を `effective` に入れる．ギャラリーから写真を保存するときに，同名のマニフェストも一緒に保存する．
  - マニフェストはギャラリーで各写真に紐付けて表示する．データセット側は，写真とマニフェストをセットで取り込む．

## 6．要件4：タブUI（済み．【v1】の追加のみ残り）

`common/webui/index.html` を，機能ごとのタブで管理する構成に改める．

- プレビューとシャッターボタンはタブの外に常時表示する（撮影しながら条件を変えるため）．
- タブの構成：「カメラ」（露出・ピント・WB・向き・撮影設定），「照明」（現行の照明ON/OFF＋OUT0〜7の個別操作），「プリセット」（既存のプリセット欄を移設．一覧・保存・適用・名前変更・削除・バンドル書き出し），「レシピ」（一覧・ステップ表エディタ・実行（【v1】試験片IDの入力を含む）・バンドル書き出し），「写真」（ギャラリー，撮影条件の表示とマニフェストの保存）．
- 選択中のタブは localStorage に覚えてよい（表示上の便宜であり，制御の状態ではないため）．
- レシピの編集は**ステップ表**で行う．1行＝1ステップ，列は 有効／シャッター（µs）／ゲイン／ピント／WB赤／WB青／照明（OUT0〜7のチェック＋「操作しない」）／画質／待機ms．
  - 「空欄は土台を継承する」を表の見出しに明記する．
  - モードの列は設けない．**シャッターかゲインのどちらかに値を入れたら，`exposure_mode` と `gain_mode` の両方を `manual` にする**（空欄の方はその時点の値で固定される）．シャッターだけ `manual` だと，ボードがゲインを自動で合わせて明るさを保つ（シャッター優先）ため，露出を変えても明るさが変わらないからである（2026-11-16 ユーザー決定．実機で確認済み）．ピント→`focus_mode`，WB赤・青のどちらか→`wb_mode` も同様に `manual` にする．値の範囲は `GET /ctrl/caps` に合わせる．
  - 行の追加・複製・削除・上下移動ができること．土台プリセットの選択（「なし＝現在設定」を含む）とレシピ名の入力，保存ボタンを置く．
- 既存機能の回帰がないこと：プレビュー（サイズ・画質），シャッター（Spaceキー含む），照明ON/OFF，露出・ピント・WBの各操作，AF，ワンプッシュWB，向き変更（再起動待ち処理），撮影設定（画質・照明），プリセット操作，設定リセット，物理ボタンの写真の自動取り込み．
